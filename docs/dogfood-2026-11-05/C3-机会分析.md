## 一、竞品已满足、牵丝尚未满足的用户需求

| 用户需求 | 竞品依据 | 牵丝缺口 |
|---|---|---|
| **图像、视频、音频等多模态生成与后处理** | comfyui：图/视频/音频/3D 节点与模板；sim：多模态生成块 | 只有文本模型家族节点，无媒体执行器 |
| **可复用、可嵌套的子工作流与模板分发** | comfyui：子图打包、嵌套、发布节点库；flowise：Execute Flow；dify：工作流资产/模板 | 缺少子工作流复用、嵌套和跨项目分发机制 |
| **画布内直接调试、修改和指挥 Agent** | comfyui：画布内 Agent；coze：节点级 Agent 会话；langflow：内嵌 Assistant | 外部 Agent 虽可通过 MCP/插件接入，但画布内缺少统一调试入口 |
| **人工审批后从断点继续** | flowise：HITL checkpoint；langflow：有状态检查点；n8n：审批相关工作流能力 | 当前验收失败即结束，缺少暂停、落盘、恢复与人工裁决 |
| **跨会话长期记忆与文档检索** | frameworks：长期 memory；dify/langflow/sim：RAG 与知识库 | 仅支持 ≤24KB 文本资料直灌，无法承载持续记忆和大型知识库 |
| **在流程中执行代码和系统命令** | dify：Linux 沙箱+Bash；n8n/sim：代码与自动化执行 | worker 目前主要产出文本，缺少受控执行环境 |
| **运行后可形成可调用的应用或 Agent 端点** | dify：发布 Web App/API；coze：多渠道发布；n8n：Agent/MCP/A2A 端点；frameworks：托管部署 | 产物只回写节点，缺少稳定发布和外部调用边界 |
| **定时、Webhook、事件驱动和无人值守运行** | coze/n8n/sim：触发器、批量与异步执行 | 明确不做定时触发，桌面关闭即停止 |
| **跨版本评估、回归测试与失败定位** | flowise：数据集评估与重跑 diff；sim：块级成本、耗时和失败追踪；frameworks：运行轨迹调试 | 验收链限于单次运行，缺少历史快照、回归和节点级追踪 |
| **第三方集成与组件生态** | comfyui：自定义节点；dify：插件市场；n8n/sim/langflow：大量 SaaS 连接器；flowise：集成目录 | 目前以自有 MCP 工具为主，缺第三方组件分发市场 |
| **多模态之外的自然语言建流** | langflow/frameworks/n8n：对话式生成工作流；coze：Vibe coding | 画布仍较依赖手工连线，缺少“生成草案—人工审阅—运行”路径 |
| **开放协议互操作** | coze：ACP；frameworks：MCP+A2A；langflow：A2A+AG-UI；n8n：MCP/A2A（部分能力待核验） | 主要是自有 MCP、插件和 OpenAI 兼容网关，跨 Agent 协议覆盖有限 |

> 精确集成数、版本号、融资与用户规模不作为需求优先级依据；部分竞品章节中的相关数字仍需回源核验。

## 二、在“本地优先、单人开发、无运维”约束下的落地分级

### P0：应裁剪落地

#### 1. 节点级调试、运行轨迹与成本追踪
**裁剪范围：**
- 每个节点展示输入、输出、耗时、Token/费用、失败原因；
- 保留结构检查、便宜闸门、完整评委各阶段结果；
- 保存运行快照，支持同一画布新旧结果 diff；
- 优先使用本地文件或 SQLite，不建设服务端监控平台。

**理由：**  
直接强化牵丝已有的“逐任务验收”差异，不需要云端、团队或长期运维，却是用户信任 Agent 结果的基础设施。实现复杂度可控，也是后续回归评估的前提。

#### 2. 子工作流复用与嵌套
**裁剪范围：**
- 节点组保存为本地模板；
- 支持模板实例化和参数绑定；
- 至少支持一层嵌套；
- 导入/导出 JSON；
- 暂不做市场、在线发布和远程版本仓库。

**理由：**  
可解决复杂画布难维护、重复编排的问题，同时保留开源和本地可移植性。应定义自己的稳定格式；ComfyUI JSON 是否值得兼容，应待格式规范核验后决定，不宜直接宣称其子图格式是事实标准。

#### 3. 节点级试跑与画布内 Agent 会话
**裁剪范围：**
- 单节点试跑；
- 查看完整提示词注入、模型回复和验收结果；
- 打开或唤起对应的 Claude Code/Codex 会话；
- 后续再增加通用 ACP worker，不急于建设完整对话式 IDE。

**理由：**  
能弥合“外部 Agent 可接入、画布内却不可操作”的断点，同时无需自己实现代码 Agent。ACP 兼容性可作为低成本扩展方向，但是否值得投入应先验证真实用户需求。

#### 4. 可暂停的人工审批点
**裁剪范围：**
- 在工具执行前、模型费用闸门前、产物最终提交前设置 checkpoint；
- 本地持久化运行状态；
- 用户放行后从断点继续；
- 首版仅支持桌面端有人在线的场景。

**理由：**  
这是高风险 Agent 工作流的核心需求，不必同时扩展成云端多人审批。后续若提供 HTTP 端点，也应明确机器无人值守时审批会阻塞。

#### 5. 运行历史转模板、版本快照与轻量回归
**裁剪范围：**
- 将成功运行保存为画布快照；
- 从快照创建模板；
- 保存固定输入与期望输出；
- 对比不同版本的结构、结果和成本；
- 评估器先支持规则、结构检查和固定测试集，不急于建设通用评测平台。

**理由：**  
把牵丝已有的单次验收转化为可积累资产，同时保持本地运行。固定数据集和人工期望输出已足以覆盖单人开发者的核心回归场景。

#### 6. 轻量文件检索
**裁剪范围：**
- 文件名、关键词、元数据召回；
- 先切片、再按需注入；
- 限定本地目录与索引大小；
- 暂不建设向量库、RAG 编辑器和企业知识库。

**理由：**  
能解决“文件太多、24KB 限制不够用”的高频问题，且可采用嵌入式索引实现。但若用户需要复杂语义召回、跨文档推理或多租户知识库，应明确超出产品边界。

#### 7. 自然语言生成画布草案
**裁剪范围：**
- 自然语言生成节点、连线和初始提示词；
- 结果必须以“草案”呈现，由用户审阅后应用；
- 不自动执行、不自动改治理策略；
- 第一阶段不做完整网页/App 生成。

**理由：**  
可降低手工编排门槛，又不必承担自动建站的托管、安全和持续维护成本。生成错误可由人工审阅消化，符合无运维定位。

### P1：有条件落地

#### 1. 本地 Agent/HTTP 调用端点
**裁剪范围：**
- 单个画布或 Agent 暴露为本地 HTTP/MCP 端点；
- 可撤销令牌、作用域和调用审计；
- 仅在本机或受控局域网运行；
- 不承诺公网托管、SLA 或自动扩缩容。

**理由：**  
可以让牵丝进入 Cursor、Claude Code、IDE 自动化等调用链，又不直接建设云服务。安全边界、并发和长任务恢复会显著增加维护成本，因此应排在运行追踪、子工作流之后。

#### 2. 受限代码执行
**裁剪范围：**
- 本地容器或受限子进程；
- 默认只读挂载、临时目录、资源上限；
- 工具调用前经过现有审批策略；
- 不提供永久在线任务和云沙箱。

**理由：**  
代码执行能显著扩展 worker 能力，但沙箱逃逸、依赖下载和跨平台差异带来持续安全负担。只应在有明确高频场景时推进，且不能伪装成零风险功能。

#### 3. Git 式版本控制
**裁剪范围：**
- 本地 Git 仓库或可导入导出的 JSON；
- 提供提交、比较、恢复；
- 不建设团队权限、分支审批和云端 Git 服务。

**理由：**  
单人开发者也需要回滚和比较，且实现相对可控。与多人协作相比，它不要求组织模型、权限体系或持续同步服务。

#### 4. ACP/A2A 等协议接入
**裁剪范围：**
- 先把外部 Agent 抽象为 worker 接口；
- 选择一个协议做适配器，而非内置多套协议栈；
- 只支持启动、传递上下文、接收结果和人工中止。

**理由：**  
协议适配可避免绑定单一 Agent，但市场成熟度与真实使用量仍需验证。资料中“事实标准”等判断没有充分依据，建议采用插件式接口并以后续验证决定优先级。

### P2：应明确放弃或仅提供外部替代

#### 1. 完整云服务与托管发布
**放弃范围：**Comfy Cloud、扣子云端、Dify Web App 托管、LangSmith Deployment、云端 Agent 长期在线。

**原因：**  
与“本地优先、零运维”根本冲突，并会引入计费、租户隔离、数据合规、弹性计算和 SLA 等持续负担。牵丝可提供本地导出、静态产物或本地端点，而不是经营云平台。

#### 2. 多人协作与完整企业权限
**放弃范围：**团队工作区、实时共同编辑、SSO/SCIM、角色组织、评论与审批流。

**原因：**  
这会要求账户体系、冲突处理、权限同步和持续运维，直接破坏单人本地定位。即使 ComfyUI 的 CRDT 共编值得借鉴，最多只做“Agent 与用户在同一画布协同”，不做多人组织系统。

#### 3. 大规模 SaaS 集成目录
**放弃范围：**n8n/sim/langflow/flowise 式数百连接器市场。

**原因：**  
连接器数量会形成持续维护债务，并依赖外部服务变化。MCP 本来就适合承载零散工具接入，牵丝应保持工具可插拔，而不是追求目录规模。

#### 4. 完整 RAG 与企业知识库
**放弃范围：**向量数据库、混合检索平台、知识库管理后台、文档权限与云端同步。

**原因：**  
该需求涉及索引生命周期、数据更新、召回质量和存储治理。首版用轻量关键词/文件检索覆盖最常用场景即可；如需复杂 RAG，应由外部工具或插件提供。

#### 5. 通用自动化触发器平台
**放弃范围：**定时、Webhook、事件触发和长期无人值守任务。

**原因：**  
需要常驻进程、任务队列、失败重试、时区调度、监控和通知，已经超出“无运维”的核心承诺。若用户确有需要，可通过本地插件或用户自行启动的外部调度器连接本地 HTTP 端点。

#### 6. 多媒体生成平台与素材云
**放弃范围：**自建 GPU 调度、媒体模型仓库、Credits、云端资产管理和商业化素材生态。

**原因：**  
这会把牵丝从 AI 编排工具变成重资产生成平台。可通过 MCP/插件调用外部媒体服务，但不承诺托管、素材库或 GPU 调度。

#### 7. 通用无代码应用生成器
**放弃范围：**一句话生成并部署网页、App、小程序，以及完整模板商店和职业技能包市场。

**原因：**  
其后续需要应用运行时、依赖升级、域名、托管、安全修复和商业化支持。牵丝可提供“生成工作流草案”，但不应承担生成应用的发布和运维责任。

## 建议的边界结论

牵丝不应成为“另一个 n8n、Dify 或 ComfyUI”。更可守的定位是：

> **面向单人开发者的本地优先 Agent 任务画布：用主控—Worker 分工、逐任务验收、运行追踪和可复用子工作流，把 Claude Code、Codex 等外部编码 Agent 编排成可调试、可回滚、可审计的本地工作流。**

优先级上，应先补齐 **运行追踪/回归、子工作流、节点级试跑、暂停审批** 四项；它们最能放大现有验收链优势，同时不要求建设云服务、多人协作或 SaaS 生态。
