# 从 Grok Bot 学到的运行方式（以及牵丝落了什么）

2026-11-12。读的材料来自 xAI 的 Grok Bot 公开资料与社区整理的现场笔记：

- 现场笔记：[unicodef1wn/grokbot-field-notes](https://github.com/unicodef1wn/grokbot-field-notes)（三位 xAI 工程师 72 小时直播构建的 AGENTS.md / VERIFICATION / ORCHESTRATION / ANTIPATTERNS）
- 社区实践：[reichenbach/grokbot-agent-bots](https://github.com/reichenbach/grokbot-agent-bots)（人类审批闸门 + 编码 agent 团队）、[aritosi/grokbot-autoloop](https://github.com/aritosi/grokbot-autoloop)（无人值守开发监督：机器人规划与验证、headless CLI 写代码、停在 PR 等人合并）、[rodrigo-pasini/grokbot-kit](https://pypi.org/project/grokbot-kit/0.1.0/)（把任务派给 headless 编码 agent，完成/出错/超时/需输入时通过 webhook 唤醒）

## 它的运行方式，一句话版

**一个 bot = 一个有名字的同事**：一份工作、自己的记忆、自己的上下文、自己的电脑。
用户一次性把标准说清楚（写进描述/技能/例行任务），bot 自己发现工作、自己干、自己验证，
拿不准或要动生产时回来要授权。团队的工程纪律可以浓缩成一句：

> 复现它、运行它、证明它；修根因不修症状；被纠正时写下通用的原则，而不是这次的故事。

## 六条真正改变设计的规则

### 1. 验证就是工作本身（Verification is the job）

写代码是简单的那一半。**没有可演示的证据就等于没做完**，无论多有把握。
他们要求每个 PR 附证明：UI 给截图/录屏，后端给前后数字，修 bug 给复现步骤。

落到牵丝：**用户视角验收**（[user-view.md](user-view.md)）——
运行结束后真的把项目跑起来、无头浏览器打开、截图、逐项检查，
而不是让评委模型看着一段文字「觉得没问题」。证据是截图和检查结果，不是分数。

### 2. 能机器判定的信号，先做成一个可重复的命令

他们给每个项目写一个 `verify` CLI（seed / run <flow> / screenshot / check），
确定性、失败退出非零、打印它做了什么；再配一份机器可读的 feature map，
让 agent 不用猜怎么进入每个流程。理由很直接：没有验证回路，每个任务都要回到人这里，
**人就变成了测试套件**。

落到牵丝：验收检查项是固定脚本（`apps/server/src/user-view.ts`），
同一个项目重复跑结果一致；`detectProject` 相当于 feature map 的最小子集——
说清楚入口在哪、怎么启动、能不能自动验收。

### 3. 两次同一方法失败，就停下上报

`AGENTS.md` 的原话：**不要在同一个方法上循环。两次失败说明方法错了，不是需要第三次。**

落到牵丝：自动重试硬上限 3 次（首跑 + 2），用尽后停止并把结论写给用户；
「失败诊断」里说明自动额度已用尽、手动重跑不占额度。
`failureSummary` 记录失败任务、分类原因和具体错误，画布与运行条都能看到。

### 4. 报告事实，不制造进度

「状态」只回答：完成了什么、在做什么、卡在哪。没有变化就说「没有变化」，
定时检查没有内容就保持安静。

落到牵丝：失败总结只在失败时生成；运行条区分「完成 / 失败 / 被中断」，
中断不会被写成「全部完成」；排队中的重跑显示「已排队」而不是假装在跑。

### 5. 把噪音挡在门外

他们的反模式清单里有一大类是「看起来像需求的东西其实不是」：
工具返回、系统注入、群聊里每个 bot 都回话。

落到牵丝：接管与转录读取过滤 tool_result、系统注入、整行方括号标记
（`[Request interrupted by user …]`）、`继续/好的` 这类短指令；
2026-11-12 又补了一条真 bug——**上下文压缩摘要**（以 `This session is being continued …` 开头）
被当成用户需求启动了一整轮；现在它和 `<system-reminder>`、粘贴占位一起被过滤。

### 6. 自治按爆炸半径分档，人工闸门永远保留

他们的「自动驾驶阶梯」：调查 → 草稿 → 自动驾驶 → 完全自动驾驶。
越是接近生产、金钱、权限，越要收回一档；自动修 bug 曾经把生产数据库打挂。

落到牵丝：工具限定在画布工作目录、危险命令拒绝、每次调用审计；
重跑与自动续跑都可被用户一键停止，停止后不再自动恢复（manualStop）。

## 团队模式：名册、幕僚长、手册广播、员工会议

他们的组织经验比单个 bot 的技巧更重要：

- **一个 bot 一件事**。不是万能助手，而是你可以点名的一组专家；
  上下文被限定在一个职责里，反馈才能真正收紧。
- **幕僚长**：你只跟一个主控说话，它把活分给专家、收齐结果再汇报。
- **手册广播**：标准只写一次，由一个成员拥有，所有成员都读；不等于复制粘贴到每个人。
- **员工会议**：把几个专家拉进同一个话题，要求他们**明确分歧**，再由主控综合。
- **自治阶梯**：调查 → 草稿 → 自动驾驶 → 完全自动驾驶；爆炸半径越大，档位越低。
- **别养一堆 bot**：新建之前先问「现有成员加个技能/例行任务行不行」；
  人越多，上下文、费用和你的注意力越多。

牵丝的落地：每张画布一份团队名册与手册（`team.json`），编排优先按职责派活，
运行时把成员身份、档位和记忆注入对应任务；调查/草稿档位在工具清单和执行器两层
被限制为只读；「团队会议」复用多模型讨论并要求带职责发言。
详见 [team.md](team.md)。

## 没有照搬的部分

- **云电脑/每 bot 一台 VM**：牵丝是本地的，工具在用户自己的项目目录里运行。
  好处是不用上传代码；代价是隔离弱——所以路径限定、命令黑名单和审计是必需品。
- **每 bot 独立记忆存 S3**：牵丝用画布 + 运行记录 + 交付物文件，不做跨会话人格记忆。
- **例行任务（routines）**：我们只保留「实时接管」这一个事件驱动的入口，
  不做按分钟轮询的常驻任务，避免 token 花在「没什么可报告」上。
- **浏览器自动化代替 API**：验收只做「用户看得到的东西」；需要调 API 的流程仍走工具。

## 参考的失败清单（直接影响了我们的取舍）

- 不变量只写在提示词里、没有测试或可见读数 → 我们的验收是显式检查项，不是一句「看起来不错」。
- 「紧急」会让 agent 跳过步骤 → 用固定上限和明确优先级代替重复催促。
- 给 agent 的指令写成「记得那天那个 z-index 问题」→ 规则写原则，删掉故事（本文件的写法也是）。
- 自动修复无人看守 → 破坏性动作永远要人批；我们只自动重跑失败运行，不做自动改代码上线。
- 频率是花钱的大头 → 实时接管用事件触发，重试用硬上限，验收按需/成功后一次。

## 对牵丝的下一步启发

1. 验收可以再往前一步：把「主要按钮有反应」升级成可配置的流程脚本（登录、下单、导出），
   让用户为自己的项目写两三条关键路径，验收按路径跑。
2. 失败诊断已经把「环境」和「任务」分开；下一步是让诊断结果直接生成修复动作清单
   （启用某厂商、改工作目录、提高预算），一键执行后重跑——目前前两项已可一键。
3. 报告语言统一：任何自动结论都带「为什么」和「证据在哪」，避免只给一个分数。
