# 反方评审：连线产物卡方案尚不能直接落地

## 方案主张复述

C1 主张把卡片改为固定尺寸、沿连线法线偏移的产物卡，以状态条、图标、任务 ID、摘要和徽标表达层级，并用短引导线与路径连接点解决“压线”。

C2 主张以固定卡片尺寸和可计算的法线偏移建立布局规格，处理短边、长边、平行边和密集图，同时保持 React Flow 画布坐标体系。

但这两份方案目前都缺少一个关键前提：**卡片的几何尺寸、屏幕显示尺寸、缩放后的视觉尺寸和避让占用区必须使用同一套坐标系。** 否则“数学上不压线”和“视觉上不压线”可能同时成立不了。

---

## 最强反对论证

### 1. 缩放失败：220px 到底指屏幕像素还是画布单位没有统一

**失败场景**

在 `zoom=0.5` 时，`EdgeLabelRenderer` 随画布缩小，卡片从屏幕上的 220px 变成约 110px；但避让算法如果仍按 220 画布单位占位，会留下巨大空洞。在 `zoom=2` 时，卡片变成约 440px，不仅遮挡其他内容，220px 的定位偏移也可能把卡片推入节点。

如果布局按 220 画布单位计算，而 CSS 又按屏幕像素显示，则“主体与连线净距至少 6px”在不同缩放下也不稳定：它可能从屏幕 3px 变成 12px。

**最可能被推翻的地方**

C2 的“固定尺寸即可预计算占位框”只在缩放恒定或显示尺寸与占位尺寸严格同比例时成立。

**可执行修正**

明确采用一种模型，推荐如下：

- 避让和偏移全部使用**画布单位**。
- 卡片保持屏幕尺寸恒定时，通过 `scale(1 / viewport.zoom)` 抵消画布缩放。
- 卡片锚点必须补偿缩放后的自身尺寸，不能继续简单使用 `translate(-50%, -50%)`。

```ts
const inverseZoom = 1 / zoom;

const style = {
  transform: `
    translate(${labelX}px, ${labelY}px)
    translate(-50%, -50%)
    scale(${inverseZoom})
  `,
};
```

如果产品要求卡片随画布一起放大，则反过来统一约定：CSS 宽度、几何占位宽度、引导线长度全部乘以 `zoom` 换算到画布单位。二者只能选一个，禁止混用。

验收条件：

- `zoom=0.25 / 0.5 / 1 / 2 / 4` 下，卡片不压线。
- 卡片与连线、节点、其他卡片的屏幕净距均不小于约定值。
- 缩放过程中卡片不出现跳位、抖动或突然换槽。

---

### 2. 短边失败：固定 220px 卡片和 8–12px 引导线在几十像素边上不可靠

**失败场景**

一条只有 40px 的边，卡片宽 220px。即使沿法线向上偏移，卡片仍可能覆盖源节点或目标节点；引导线连接点落在路径上，也无法解决卡片横向覆盖节点的问题。

另一个失败场景是源节点与目标节点垂直相邻：卡片向上偏移后可能直接盖住源节点。若自动翻转到下方，又会盖住目标节点。此时继续增加偏移距离只会扩大冲突。

**最可能被推翻的地方**

C1 的“短边只用 8–12px 引导线即可”以及 C2 默认存在的“可用法线外侧区域”，对短边和节点夹逼场景不成立。

**可执行修正**

短边不能只采用单卡偏移，必须分为两类：

1. **仍显示完整 220px 卡片**：进入“节点外侧槽位”布局。
2. **空间不足**：进入“紧凑卡模式”，而不是硬塞完整卡。

紧凑卡规则：

```tsx
const compact = availableNormalSide < MIN_CARD_HEIGHT + 2 * CLEARANCE;

<button
  className={`artifact-card ${compact ? 'artifact-card--compact' : ''}`}
>
```

```css
.artifact-card--compact {
  width: 168px;
  padding: 6px 8px;
}

.artifact-card--compact .artifact-card__summary {
  display: none;
}
```

节点夹逼时，卡片中心沿边的方向继续移到源/目标节点外侧，而不是只向法线移动：

```ts
const shortEdgeOffset = Math.max(
  0,
  CARD_SCREEN_WIDTH / 2 + NODE_CLEARANCE - edgeLength / 2
);
```

验收条件：

- 40px、80px、120px 边均不覆盖节点。
- 卡片连接点仍落在真实路径上。
- 引导线超过 24px 时自动转为紧凑卡或槽位卡片，不保留长“悬空线”。

### 3. 密集图失败：逐边独立偏移无法解决平行边和多卡抢占

**失败场景**

同一对节点之间有三条平行边，每条边都按相同法线向上偏移，会得到三个相同槽位，三张卡完全重叠。若仅检测“同一条边附近”，也无法处理来自不同节点、但占据同一屏幕区域的卡片。

更严重的是，如果每条边在 React 渲染期间临时测量 DOM 来避让，后渲染的卡会把先渲染的卡推走，缩放或节点移动时产生持续抖动。

**最可能被推翻的地方**

C2 中“固定尺寸后即可计算避让”的推导不充分。**尺寸固定只能支持计算，不能自动得到全局无冲突布局。**

**可执行修正**

不要让每条 `ArtifactEdge` 独立决定最终槽位。由图布局层统一计算：

```ts
interface ArtifactSlot {
  edgeId: string;
  side: 'up' | 'down' | 'left' | 'right';
  dx: number;
  dy: number;
}

function allocateArtifactSlots(
  edges: ArtifactEdgeInput[],
  viewport: { zoom: number }
): Map<string, ArtifactSlot> {
  // 1. 标准化到画布坐标
  // 2. 候选方向排序
  // 3. 以“卡片占位矩形”做冲突检测
  // 4. 优先复用已占用槽位之外的候选位置
  // 5. 无法解决时标记 compact 或隐藏摘要
}
```

最低限度冲突检测应基于矩形，而非点：

```ts
function intersects(a: Rect, b: Rect, gap = 12): boolean {
  return !(
    a.x + a.width + gap <= b.x ||
    b.x + b.width + gap <= a.x ||
    a.y + a.height + gap <= b.y ||
    b.y + b.height + gap <= a.y
  );
}
```

候选槽位顺序示例：

1. 首选法线正方向；
2. 对侧；
3. 沿边方向偏移后的侧向槽位；
4. 外侧紧凑槽位；
5. 无法分配时只显示状态图标卡。

验收条件：

- 三条平行边必须得到三个不重叠槽位。
- 节点移动、缩放时卡片不发生反复弹跳。
- 冲突缓解只能降级展示，不能导致整张图持续重排。

### 4. 长文本失败：按字符截断不是按视觉行数截断

**失败场景**

`slice(0, 42)` 遇到中文、英文、URL 或连续空格时，占用宽度差异很大。42 个窄字符可能只占半行，42 个宽字符则可能溢出。`line-clamp: 2` 只有在容器宽度、字号和字体加载完成后才知道实际行数。

如果字体加载较慢，初始文本高度会变化；如果卡片高度固定为单值，两行摘要可能裁掉第三行，或者卡片高度与占位估算不一致。

**最可能被推翻的地方**

C1 的“摘要 42 字 + `line-clamp: 2`”不能保证固定高度和稳定几何占位。

**可执行修正**

保留字符截断作为数据保护，但必须同时使用固定摘要高度：

```tsx
<span className="artifact-card__summary" title={artifact.output}>
  {artifact.output.replace(/\s+/g, ' ').trim()}
</span>
```

```css
.artifact-card__summary {
  display: -webkit-box;
  -webkit-line-clamp: 2;
  line-clamp: 2;
  -webkit-box-orient: vertical;
  overflow: hidden;
  min-height: 30px;
  max-height: 30px;
  overflow-wrap: anywhere;
}
```

卡片高度必须固定：

```css
.artifact-card {
  height: 84px;
}
```

不要用 `slice(0, 42)` 作为唯一截断策略。完整 `output` 应进入可访问名称或详情面板；`title` 只能作为补充。

验收条件：

- 42 个中文字符、42 个 URL、含 emoji 和零宽字符时均不改变卡片尺寸。
- 两行以上文本被视觉截断。
- 键盘和读屏用户能够获得任务 ID、状态及详情入口；不能依赖 hover 标题。

### 5. 键盘可达性失败：按钮可聚焦不等于用户能理解焦点落在哪里

**失败场景**

`focus-visible` 使用外描边，但卡片靠近节点、画布边缘或被其他元素遮挡时，outline 可能被父级裁剪。键盘用户 Tab 到卡片时，如果画布没有自动滚动，焦点可能仍停留在屏幕外。

此外，多条产物卡可能按 React Flow 边的 DOM 顺序排列，而不是按空间顺序排列；这会形成不连续、难以预测的 Tab 路径。`aria-label` 仅描述“打开某任务”，没有状态和摘要，不能让读屏用户在列表中快速区分卡片。

**最可能被推翻的地方**

C1 的“使用原生 button + focus-visible 即保证键盘可达”只解决了可聚焦，没有解决焦点可见、顺序和语义完整性。

**可执行修正**

1. `aria-label` 必须包含任务 ID、状态和摘要。
2. 详情打开后，焦点移入面板；关闭后回到原卡片。
3. 画布容器不得裁剪卡片焦点环。
4. 键盘打开时提供明确反馈。
5. 若支持 Escape 关闭详情，应在面板内处理。

```tsx
const label = [
  `任务 ${artifact.taskId}`,
  `状态：${badgeText}`,
  artifact.output.replace(/\s+/g, ' ').trim()
].join('，');

<button
  aria-label={label}
  aria-haspopup="dialog"
  onKeyDown={(event) => {
    if (event.key === 'Escape') {
      event.currentTarget.blur();
    }
  }}
>
```

```css
.artifact-card:focus-visible {
  outline: 2px solid #6ea8fe;
  outline-offset: 3px;
  z-index: 20;
}
```

详情面板应使用 dialog 语义并实现焦点约束；关闭后恢复触发按钮焦点。

验收条件：

- 仅用键盘可打开、阅读并关闭详情。
- 焦点不会落到视口外。
- 多个状态和任务在读屏列表中可区分。
- 不依赖颜色、hover 或 `title` 传达状态。

---

### 6. 性能失败：每条边独立求切线、占位和碰撞会把复杂度放大到全图

**失败场景**

几十条产物边在节点拖动时全部重渲染。若每条边都重新解析 `path d`、计算法线、枚举候选槽位并做全图矩形冲突检测，成本近似为：

```text
边数 × 候选槽位数 × 其他卡片数
```

例如 50 条边、每条 8 个候选、50 张卡，仅冲突检测就接近 20,000 次矩形比较；拖动过程中若同时触发 React Flow 渲染，容易出现掉帧。

直接解析 `getSmoothStepPath` 生成的字符串也脆弱：路径格式、命令顺序或库版本变化，都可能让正则解析失效。

**最可能被推翻的地方**

C2 的“不做 DOM 测量后布局”避免了抖动，但若改成每条边重复字符串解析和全局搜索，并不能保证性能。

**可执行修正**

- 在图级统一计算一次槽位；
- 按边 ID 和几何参数缓存结果；
- 布局计算与卡片渲染分离；
- 优先使用 React Flow 提供的路径元素或明确、可测试的路径解析器；
- 冲突检测按空间网格分桶，避免全量两两比较。

```ts
const slotCache = new Map<string, ArtifactSlot>();

function getArtifactSlot(edge: ArtifactEdgeInput): ArtifactSlot {
  const key = [
    edge.id,
    edge.sourceX,
    edge.sourceY,
    edge.targetX,
    edge.targetY,
    edge.zoomBucket
  ].join(':');

  const cached = slotCache.get(key);
  if (cached) return cached;

  const slot = computeArtifactSlot(edge);
  slotCache.set(key, slot);
  return slot;
}
```

缩放值不应作为精确布局缓存键；应按布局阈值分桶，例如每 0.1 一档，避免连续缩放触发无限缓存增长。

验收条件：

- 50 条产物边拖动时无明显卡顿。
- 路径库升级后有解析回归测试。
- 缓存条目有上限或生命周期，不能无限增长。

## 对 C1 各结论的“最可能被推翻的地方”

- **“不再钉在 labelX/labelY”**：不准确。卡片仍需锚定到路径附近；若只是固定沿法线平移，平行边仍会重叠。
- **“固定 220px 宽”**：在画布缩放下会变成可变屏幕尺寸；必须明确是否使用逆缩放。
- **“摘要最多两行”**：未指定固定摘要高度和 `overflow-wrap` 时不能保证几何稳定。
- **“颜色 + 图标 + 文字三重表达”**：若徽标只显示“通过/未通过”而无任务语境，读屏标签仍可能不够清晰。
- **“引导线 8–12px”**：短边、节点夹逼和卡片翻转时可能不足。
- **“原生 button 即保证可达”**：未处理焦点管理、面板焦点回归及焦点裁剪。
- **“不引入依赖”**：合理，但不能以手写解析复杂 SVG path 为代价；应限制到 React Flow 当前实际生成的路径子集并加测试。

## 对 C2 各结论的“最可能被推翻的地方”

- **“卡片尺寸固定即可预计算”**：前提是尺寸与缩放模型统一；否则只消除了内容撑开这一种不确定性。
- **“只有 d 和 label 坐标，必须自己求切线”**：技术上不等于可以安全地靠字符串猜测；字符串解析是明显单点故障。
- **“禁止 DOM 测量”**：避免布局抖动是对的，但几何求解不能同时依赖 DOM 时，必须有可靠的解析路径。
- **“无碰撞逻辑导致重叠”**：正确；但只补碰撞检测而不建立全局槽位分配，仍会抖动。
- **“几十条带产物边”**：规模不大，但若每边进行全局冲突搜索，拖拽时仍可能成为瓶颈。
- **“节点和其他卡片避让”**：若只处理卡片与卡片、不处理卡片与节点包围盒，短边仍会失败。

## 风险清单与触发条件

| 风险 | 触发条件 | 必须触发的修正 |
|---|---|---|
| 缩放后卡片尺寸失真 | `zoom` 不在 `0.5–2` | 逆缩放固定屏幕尺寸，或统一换算全部几何量 |
| 卡片遮挡节点 | 边长小于约 220px，或节点垂直相邻 | 紧凑卡 + 沿边方向外移 |
| 平行边卡片重叠 | 同一对节点存在两条以上产物边 | 图级槽位分配器 |
| 长文本撑高 | 字体延迟、URL、中文宽字符 | 固定高度、line-clamp、`overflow-wrap:anywhere` |
| 键盘焦点不可见 | 父容器裁剪、焦点位于视口外 | 禁止裁剪、滚动聚焦、焦点回归 |
| 详情打开后焦点丢失 | 面板关闭未管理焦点 | dialog 焦点约束，关闭后返回按钮 |
| 拖动或缩放卡顿 | 每边独立解析路径并全局碰撞 | 图级计算、缓存、空间分桶 |
| 路径解析失效 | React Flow 改变 path `d` 格式 | 锁定版本并添加路径解析回归测试 |
| 连接点不再落在线上 | 卡片翻转后仍复用底部 tether | 每种方向分别计算 tether 起点和终点 |

---

## 该主张在什么条件下才成立

上述方案只有同时满足以下条件，才可以进入实现：

1. **坐标系唯一**：偏移、占位矩形、引导线和 CSS 尺寸全部明确采用屏幕像素或画布单位中的一种。
2. **卡片显示尺寸稳定**：缩放时选择固定屏幕尺寸或全量同比缩放，不允许两者混用。
3. **槽位由图级统一分配**：单条边不能自行决定最终位置。
4. **路径切线来源可靠**：不能依赖未经验证的脆弱字符串解析；若必须解析，只能支持并测试当前库实际生成的 path 子集。
5. **短边有降级方案**：至少包含紧凑卡和沿边外移，不能假设任意边都有法线空间。
6. **摘要区域高度固定**：长文本不得改变卡片占位尺寸。
7. **键盘路径完整**：可聚焦、焦点可见、打开详情后焦点进入面板，关闭后返回原卡。
8. **布局计算可缓存**：节点或缩放未变化时不重复进行全图求解。
9. **可访问性不依赖颜色或 title**：状态、任务 ID、摘要和详情入口均进入可访问名称。
10. **验收覆盖极端场景**：至少包含 `zoom=0.25/0.5/1/2/4`、40px 短边、100px 短边、三条平行边、50 条产物边、URL/中文长文本、纯键盘操作。

在这些条件未落实前，“固定尺寸 + 法线偏移 + 短 tether”只能算视觉草案，不能称为可直接实现的不压线布局规格。
