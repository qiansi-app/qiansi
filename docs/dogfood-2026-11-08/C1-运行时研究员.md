# dsh-superagent-prototype 运行时/会话/工具注册架构研读报告

**研读员：运行时研究员**。素材：dsh-runtime.md、dsh-sessions.md（截断）、dsh-tool.md（截断）、web 查证。范围：组合根、生命周期、会话装饰与工具注册。授权/执行模型由另一位研读员负责，本报告不越界下结论。

## 一、先说听懂的版本（共识性理解）

dsh-superagent-prototype 不是独立 agent runtime，而是挂在 DeepSeek Harness（Cordis 容器）上的一个 **bundle**。它自己的 `Runtime`（组合根，约 254 行）只做三件事：**接事件、判授权、把活派给 Session**，agent 执行能力全部来自 `@deepseek-ai/*` 一组 peer 依赖（dsh 0.2.1 预发布版，Node 22.19/24，MIT，仓库单提交 6337fc8）[zhihu 解读](https://zhuanlan.zhihu.com/p/2100546420642144518)。

运行时核心形状：

- **单进程单写者**：启动先对 `machine.stateDir` 上 `proper-lockfile` 锁（stale 30s），锁内打开 SQLite，关库后才放锁。锁被 compromise 时 `AbortController` 直接 abort 掉整个应用生命周期。
- **两段式会话**：一个常驻 **master/orchestrator 会话**（`Sessions.ensure(masterId, ..., 'orchestrator')`，id 持久化在 KV），加每个 ticket 一个 **worker 会话**（`workerSessionId(ticket.id)` 映射）。这与公开解读里的 "Router–Worker 双层结构" 完全对应 [腾讯云解读](https://developer.cloud.tencent.com/article/2774420)。
- **组合根接线**：`Store / Setup / Prompts / Effects / Sources / Commands / Sessions / Settings / DshExecutor / MasterAssessor / Outbox / Engine / Passes / HealthBoard` 全部在 `Runtime` 构造函数里组装，依赖以 **Pick 子集接口 / 角色化 getter** 注入，典型胶水层模式 [架构解析](https://blog.gitcode.com/9f5e571c749fac6c411465f9a796abd3.html)。
- **启动顺序**：`setup.run()` 失败时只注册 HTTP 路由、把健康项置为 `paused/setupPending`，**不启动任何后台循环**；配置完成后才 `sessions.install()` → `executor.install()` → 建 master 会话 → 同步策略源 → `executor.resume()/passes.start()/effects.start()`。

对牵丝最直接的启示一句话：**运行时是"接线 + 生命周期"，领域决策全在 Engine，执行全委托给 dsh 的 agent/session plug-in**。

## 二、注意到的细节（这是我的研读判断，非共识结论）

### 1. 工具注册：按会话角色切换，而不是全局注册表

核心在这一行：

```ts
tools: (agent, ticket) => ticket ? executorTools(this.toolHost, ticket) : mainTools(this.toolHost, agent)
```

工具不是挂在全局 registry 上的静态列表，而是 **`(agent, ticket?) => Tool[]` 工厂函数**，注入给 `Sessions`。同一个 `toolHost`（内含 engine/store/prompts/sessions/settings/assessor/resources/github 上下文）按"主会话 vs worker 会话"产出两套工具。从 dsh-tool.md 切片也可见工具是 `Tool<S extends z.ZodSchema>` + zod schema 形式，`registerTool` 说明它是注册器模型。

我的判断：这种"工具工厂随会话身份切换"是它能做 **最小注意力消耗** 的关键——主会话不拿执行类工具，worker 不拿授权/分配类工具。这一点值得牵丝参考，但需注意：**工具注册的完整生命周期（何时 dispose、能否热替换）在切片里没有完整展示，不能下结论说它支持热更新。**

### 2. `quiet` 回音抑制：整数计数器而非布尔

```ts
quietly: run => { this.quiet++; try { return run() } finally { this.quiet-- } }
```

main-session 工具执行 Engine 命令时，把 `this.quiet` 加一，`emit` 回调里 `this.quiet ? undefined : eventNotice(...)` 就**抑制自己触发的领域事件再通知主会话**。细节：用整数不是布尔，说明嵌套调用可重入——这是生产级细节，也是牵丝做"画布节点触发事件回声"时直接可借鉴的形态。

### 3. domain event 的路由在组合根兜底

Engine 的 `emit` 回调里做完事件→通知的最后一公里：

- `trigger.received / ticket.resumed / trigger.followup` → `followupNotice` → `sessions.relay(...)`（让主会话在同一事务里听到）
- `ticket.ended` 且是 PR 结束时 → `pullEndNotices` → `outbox.send(...)`（回到原对话交付 PR）

注意这是**组合根里的异步后处理**，不是 Engine 内部做会话投递——Engine 只发事件，投递策略留在根里。这个分层我很认可，但也想说：`emit` 回调已经比较长了，牵丝照搬时要权衡组合根会不会膨胀。

### 4. 生命周期对称 dispose + `stopped` 信号贯穿全局

- `lifetime: AbortSignal` 贯穿 Store/Sessions/Executor/Commands，停下时一个 abort 取消"运行中的读和子进程"。
- `disposers` 数组收集所有可释放资源（HTTP 路由等），shutdown 时 `reverse()` 调，保证 LIFO 释放。
- shutdown 顺序有明确因果注释：**先 cancel 所有 agent（含 worker 的 subagent），否则 worker 结束会再触发 worker turn，而工具限制此时已释放**。这是从坑里提炼出来的顺序，牵丝做多 agent 停机时值得原样吸收。
- `stopping ??= this.shutdown()`：幂等关停，并发 stop 共享同一个 Promise。

### 5. 模块级"类型空导入 + module augmentation"注册

大量 `import type {} from '@deepseek-ai/dsh-*'`，作用是把各 bundle 的**类型补丁（module augmentation）带进作用域**，比如 `declare module '@deepseek-ai/cordis' { interface Context { orchestrator: SourceHost } }`，以及 `Events` 接口的增强。也就是说：**插件之间的契约靠类型叠加拼起来，组合根不显式 new 这些插件**。这是 Cordis 生态的惯例，但对不熟悉 TS 模块增强的读者容易误读成"没用的空导入"。

### 6. Sessions 是"装饰器 + 生命周期 holder"

从 dsh-sessions.md 切片看，`Sessions` 职责浓缩为："Lifecycle, prompt/tool/skill decoration, message delivery, and budget retry tracking"。内部有：

- `SessionBinding { disposers; scope?; skills?; subagent? }`——每个被装饰 agent 的 prompt section、工具、skill scope 都带 releaser，可整体拆除；worker subagent 只挂 tool limits。
- `SessionsHost.tools(agent, ticket?)` 是依赖注入点，与 runtime 里 `mainTools/executorTools` 呼应。
- `RetryHealth` + `models` health entry：模型预算不足时的重试状态被显式健康化。
- 预设常量 `WORKER_PRESET = 'dsh-superagent-worker'`、`ROUTER_PRESET = 'dsh-superagent-router'`，由 bundle 的 patch 定义——再次证明这是 Harness 插件式扩展，而不是自研运行时。

不确定处：**prompt section 与 skill scope 的具体挂载/释放顺序、预算重试的参数语义（切片截断）**，以上只到接口形状。

### 7. paused 全局门：先接收，不处理

```ts
private paused(): boolean { return !this.setup.configured() || this.store.settings().paused }
```

"Hold evaluation, dispatch, and outbound delivery while paused or awaiting setup; sources still record incoming triggers." ——评估、分发、外发全部停，但 Source 仍记录输入。这是一个很干净的"欠配/暂停态"，牵丝的本地画布在多模型服务不可用或用户暂停时可以参考。

## 三、对牵丝优化提案的"信号清单"（供提案员筛选，非最终提案）

以下是从架构中提取的可迁移模式。是否已借鉴请按牵丝自有清单排除，我不越位：

1. **工具随会话角色二分的 tool 工厂**：`ticket ? executorTools : mainTools`，配合 `toolHost` 注入。
2. **状态目录锁 + 库在锁内启闭 + abort 生命周期**：节点进程/本地 SQLite 单写。
3. **`quiet` 可重入回音抑制**：适用于画布节点的自触发事件。
4. **组合根 emit 回调分层**：Engine 只发领域事件，会话通知/外发最后一步在根里由 `quiet` 门控。
5. **`disposers` LIFO + 幂等 `stop()` + 停机顺序因果注释**。
6. **master 会话 id 持久化（KV）+ `ensure` 幂等重建**：重启恢复"常驻实体"。
7. **`paused` 全局门 + Source 仍记录输入**。

## 四、未定项与分歧标注

- **共识**：Runtime 是组合根；会话/工具按 master–worker 二分；进程单写锁；优雅停机顺序是显式工程决策。
- **仅我的判断**：`quiet` 整数化是为嵌套可重入、domain-event 投递放组合根是分层偏好、工具工厂按会话切换是"最小注意力"的关键杠杆——这三点是从代码语义推断的设计意图，原作者未在切片内明说。
- **不确定/未核实**：dsh-sessions.md 与 dsh-tool.md 截断后，session 挂载顺序、RetryHealth 参数、tool 原语完整 schema、授权/执行模型都未在本次切片内补全；web 查证以第三方解读为主，我**未直接打开 GitHub 源码文件逐行核对**，文件级结论只到 `src/app/runtime.ts` 这个路径层次 [gitcode 解读](https://blog.gitcode.com/51f56e8d31cd4a51f25f9d6266bb12b5.html)，不声称仓库里就是 254 行（254 行来自上传资料包）。
