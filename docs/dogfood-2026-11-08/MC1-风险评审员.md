# 多工作区方案反方评审

## 方案主张复述

现有设计以 `~/.qiansi/workspaces/<id>/canvas.json` 隔离画布，并通过 `workspaceId` 绑定运行记录与产物回写；兼容旧客户端时，未知或缺失的工作区 ID 回落到当前工作区；旧版单画布首次启动迁入 `workspaces/main`。

该主张只证明了“目录已拆开”，并未证明“请求、运行、MCP、SSE、迁移和深链在并发及异常情况下仍然指向同一工作区”。

---

## 一、并发写同一工作区：最后写入者覆盖前者

**反对论证**

当前 `CanvasStore.apply()`、全量 `write()` 与 `persist()` 都没有展示工作区级锁、版本号或 compare-and-swap。多个标签页同时编辑同一工作区时，后写入者会覆盖先写入者的修改。

**具体失败场景**

1. 标签页 A 读取版本 V1，增加节点 A；
2. 标签页 B 仍基于 V1，增加节点 B；
3. A 写回 V2；
4. B 写回自己的 V2′，节点 A 被静默删除。

运行回写若使用全量 `write()`，会直接覆盖用户在同一工作区的并发编辑。

**可执行修正**

- 在每个工作区目录增加独立锁文件，例如 `canvas.json.lock`；
- 所有读改写和运行产物回写通过同一把工作区锁执行；
- 写入前校验 `canvas.revision` 或文档版本，不一致则返回 `409 workspace_conflict`；
- 运行产物回写采用基于 revision 的原子补丁，禁止无条件全量覆盖；
- 锁必须覆盖“读取当前文档 → 合并产物 → 写临时文件 → rename”的整个事务；
- 对跨进程锁补充进程退出、陈旧锁超时和人工解锁机制。

**不要做什么**

- 不要仅依赖单进程内存锁；
- 不要让 SSE、MCP、HTTP 直接绕过画布存储层写文件；
- 不要用 `last-write-wins` 作为冲突策略而不提示用户。

**最可能被推翻的地方**

“每个工作区目录独立，所以并发安全”——目录隔离只能隔离文件，不能解决同一目录内的写竞争。

---

## 二、跨工作区回写：运行快照与当前工作区可能混淆

**反对论证**

虽然 `writeRunArtifacts` 使用发起时记录的 `runWorkspace`，但仍需验证快照、计划、产物和重试链是否全部使用同一 ID。当前 `store.create(runId, ..., workspaceOf(context))` 和其他创建路径如果在执行过程中再次读取“当前工作区”，就可能发生漂移。

**具体失败场景**

用户在 A 工作区发起运行，随后切换到 B；异步规划器调用 `workspaceOf(context)` 时，若请求没有工作区头，就会解析为 B。任务随后读取 B 的画布，产物却写入 A，造成内容污染。

**可执行修正**

- 启动任务时生成不可变 `runContext`：

  ```ts
  { runId, workspaceId, sourceRevision, startedAt }
  ```

- 整个任务生命周期只使用 `runContext.workspaceId`，不得再次调用 `workspaces.current()` 或 `resolve(undefined)`；
- 将工作区 ID 写入运行记录的必填字段；旧记录仅在兼容路径映射为 `main`；
- 产物回写前检查 `run.workspaceId === targetWorkspaceId` 且任务未结束；
- 跨工作区回写必须显式接收 `targetWorkspaceId`，并单独授权与审计；
- 为每个运行增加 workspace-scoped 幂等键，防止重试重复应用产物。

**不要做什么**

- 不要让后台任务依赖全局“当前工作区”；
- 不要把“运行发起时的工作区”和“产物落点”分成两个可漂移的变量；
- 不要因目标不存在而自动回落到当前工作区。

**最可能被推翻的地方**

“产物会写回发起工作区”——只有所有异步阶段都使用不可变的运行工作区 ID 时才成立。

## 三、MCP 无参调用回落：兼容逻辑会写错项目

**反对论证**

`resolve(undefined)` 回落当前工作区适合旧客户端“读取”，但不适合写操作。不同 MCP 客户端、自动化任务或用户切换工作区后，无参写入可能落到错误项目。

**具体失败场景**

用户让 MCP 在工作区 A 添加节点，但 MCP 工具没有 workspace 参数；用户此时切到 B。无参调用被回落到 B，节点被写入 B，而调用日志只显示“添加节点”。

**可执行修正**

- 所有 MCP 写工具增加必填或可验证的 `workspace_id`；
- 若服务端无法判断是否已有活动任务上下文，无参写入返回 `400 workspace_required`，不得回落；
- 读取类工具可保留无参兼容，但响应必须包含：

  ```json
  { "workspace_id": "ws-xxx", "resolved_by": "explicit" }
  ```

- MCP 会话建立时绑定工作区，并在切换时要求重新确认；
- 对 `create/delete/apply/run/write_artifacts` 禁止隐式回落；
- 兼容期内记录 `resolved_by: "fallback"`，便于发现误写。

**不要做什么**

- 不要为“方便兼容”让写工具默认操作全局当前工作区；
- 不要仅在工具描述中要求传参，却不在服务端校验；
- 不要让无参工具在多个候选工作区之间猜测。

**最可能被推翻的地方**

“未知工作区回落当前工作区即可兼容”——该策略对读取尚可，对写入会制造不可检测的跨项目污染。

## 四、迁移丢数据：索引损坏触发重复迁移，失败后仍创建新索引

**反对论证**

当前逻辑在 `workspaces.json` 损坏或缺少有效 `items` 时，会重新执行迁移。若 `workspaces/main/canvas.json` 已存在但旧 `canvas.json` 也仍存在，代码会删除旧文件；若目标文件已存在但内容损坏，则可能保留损坏目标并删除仍完好的旧文件。

此外，迁移完成后立即创建新的 `workspaces.json`。迁移中途崩溃可能留下：

- 旧文件仍在；
- 新文件已部分存在；
- 新索引已生成；
- 下次启动因为索引有效而不再迁移。

这会产生孤儿文件或错误的数据可见性。

**具体失败场景**

迁移时 `canvas.json` 成功移入新目录，但 `canvas.revision` 移动失败；程序随后创建索引并正常启动。系统认为迁移完成，但 revision 不匹配，后续写入或冲突检测失效。另一个场景是目标 `canvas.json` 已存在且内容损坏，旧文件完整；现有分支可能直接删除旧文件。

**可执行修正**

- 迁移前生成备份：

  ```text
  canvas.json.bak
  canvas.revision.bak
  ```

- 不删除任何源文件；复制并校验成功后再保留备份；
- 校验迁移前后文件大小和内容摘要一致；
- 使用迁移状态文件，明确记录 `pending/completed`；
- `completed` 前不得仅因新索引存在就跳过恢复；
- 若目标已存在，比较摘要：
  - 相同：保留目标；
  - 不同：停止迁移并报告冲突，禁止删除源文件；
- 启动时自动扫描孤儿旧文件并提示恢复；
- 索引写入失败时保留旧索引，不得用空索引覆盖。

**不要做什么**

- 不要在无法确认目标内容有效时 `rmSync(from)`；
- 不要把“索引文件存在”视为迁移完成的唯一依据；
- 不要静默重建损坏索引。

**最可能被推翻的地方**

“迁移只做一次且不丢数据”——现有代码只能证明正常路径，不足以证明部分失败和重复启动路径安全。

## 五、SSE 串台：按运行 ID 订阅不足以隔离工作区

**反对论证**

`/api/runs/:id/events` 如果只按运行 ID 过滤，多个工作区中相同或可枚举的运行 ID、客户端重连、进程内事件总线复用，都可能造成事件串台。SSE 还可能先发送“当前状态快照”，随后再发送实时事件；若两者工作区口径不一致，更新会混合。

**具体失败场景**

工作区 A 的运行 `r1` 正在执行，客户端连接 `/api/runs/r1/events`。运行完成事件到达后，该连接又收到工作区 B 的全局广播，因为事件总线按连接或任务类型分发而未检查 `workspaceId`。客户端会错误地把 B 的节点状态应用到 A。

**可执行修正**

- 每条 SSE 事件加入：

  ```json
  {
    "event_id": "...",
    "run_id": "...",
    "workspace_id": "ws-xxx",
    "revision": 12,
    "type": "..."
  }
  ```

- 建立连接时解析运行的不可变 `workspaceId`，订阅时按 `runId + workspaceId` 双重过滤；
- 心跳、重连提示、错误事件也必须带相同工作区上下文；
- 客户端发现事件 `workspaceId` 或 `revision` 不匹配时立即丢弃并重新拉取快照；
- SSE 响应设置正确缓存策略，并禁止代理缓冲；
- 优先使用 `Last-Event-ID` 恢复，并保证事件重放仍按工作区过滤；
- 若运行 ID 全局唯一，接口仍应验证 URL 中运行记录所属工作区与请求工作区一致。

**不要做什么**

- 不要仅依赖运行 ID 隔离；
- 不要向 SSE 广播未携带工作区上下文的事件；
- 不要在重连时无条件发送全局最新画布。

**最可能被推翻的地方**

“运行有 workspaceId，所以 SSE 不会串台”——只有事件生产、分发、重放、客户端消费全链路都校验工作区时才成立。

## 六、其他必须阻断的风险

### 6.1 工作区 ID 可造成目录穿越

`dirOf(id)` 直接拼接路径；如果 `id` 可来自 header、query 或 URL，就应防止 `../`、绝对路径及符号链接逃逸。

**修正**

- 生成工作区 ID 时使用不可预测随机值；
- `dirOf()` 仅接受严格匹配的服务端生成 ID；
- 对所有入口统一验证 `id` 格式；
- `resolve()` 遇到非法 ID 返回错误，不得回落后执行写入。

**不要做什么**

- 不要仅用 `join()` 就认为已防止路径穿越。

**最可能被推翻的地方**

“索引只保存受控 ID”——外部请求仍可能直接提供任意 ID。

### 6.2 删除工作区与运行回写存在竞态

**具体失败场景**

任务运行时删除工作区，任务结束后按旧目录回写，可能重新创建目录或写入孤儿产物。

**修正**

- 删除前检查运行状态；存在活动运行时返回 `409 workspace_busy`；
- 写入前再次验证工作区仍存在且未标记删除；
- 删除采用 tombstone 标记，后台任务不得复活已删除工作区。

**不要做什么**

- 不要先删目录，再允许迟到任务重新创建它。

**最可能被推翻的地方**

“回写始终落在原工作区”——原工作区可能已被删除或迁移。

### 6.3 接续会话固定写“当前”工作区

**反对论证**

`/api/handoff` 永远写当前工作区，会把 A 的会话摘要导入用户随后切换到的 B。若产品意图是“继续原会话”，这属于确定性串项目。

**修正**

- handoff 请求显式携带 `sourceWorkspaceId` 和 `targetWorkspaceId`；
- 默认目标为来源工作区，而不是全局当前工作区；
- 跨工作区导入必须由用户确认；
- 响应返回实际来源和目标 ID。

**不要做什么**

- 不要静默使用 `workspaces.current()` 作为 handoff 目标。

**最可能被推翻的地方**

“接续会话已正确绑定”——当前实现并未绑定。

### 6.4 VS Code 深链不能指定工作区

**反对论证**

用户从 A 工作区复制深链，在另一窗口打开时只能进入全局当前工作区，链接不可复现。

**修正**

深链加入已编码的工作区标识，例如：

```text
vscode://qiansi/open?workspace=ws-xxx&run=...
```

接收端验证 ID；工作区不存在时明确提示“工作区不存在”，不得打开当前工作区。

**不要做什么**

- 不要把未知 ID 降级为当前工作区后显示成功。

**最可能被推翻的地方**

“深链可定位对应项目”——尚无工作区定位能力。

---

## 该主张成立的条件

上述设计只有在以下条件全部满足时，才能声称多工作区可靠：

1. 每个请求或工具调用都得到确定的工作区 ID；写操作禁止无参回落。
2. 同一工作区的读改写、运行回写、迁移和删除受同一并发控制机制保护。
3. 运行上下文中的 `workspaceId` 不可变，异步链路不读取全局当前工作区。
4. SSE 的生产、过滤、重放和消费都携带并校验工作区 ID。
5. 迁移可重复执行、可恢复、保留源文件，并能检测目标冲突。
6. 删除、切换、迁移期间不存在后台任务复活目录或写错目标的窗口。
7. 工作区 ID 在所有外部入口均经过严格验证，不能形成路径穿越。
8. handoff 和深链明确表达来源及目标工作区，不以全局当前值替代。

# 可执行验收清单

## 工作区隔离

- [ ] 创建两个工作区，分别写入同名节点，读取结果互不影响。
- [ ] 工作区 A 的请求缺少 ID 时，读操作明确返回或标记回落；写操作返回 `workspace_required`。
- [ ] 非法 ID、未知 ID、路径穿越字符串均不能读写其他目录。
- [ ] 切换工作区后，前端所有读写请求都携带明确的工作区 ID。

## 并发与冲突

- [ ] 两个进程同时修改同一画布，检测到 revision 冲突且返回 `409`，不静默覆盖。
- [ ] 用户编辑与运行产物回写并发时，产物以补丁方式合入，不覆盖用户修改。
- [ ] 锁覆盖完整读改写事务；进程崩溃后存在可检测、可恢复的陈旧锁。
- [ ] 跨工作区回写必须显式指定目标并记录审计日志。

## 运行链路

- [ ] 在 A 发起运行，切换到 B 后，运行仍读取并写回 A。
- [ ] 运行记录的 `workspaceId` 不可被后续请求或重试修改。
- [ ] 工作区删除期间存在活动运行时，删除被拒绝或任务被可靠取消。
- [ ] 迟到任务不能重新创建已删除工作区目录。

## MCP

- [ ] 所有 MCP 写工具在 schema 和服务端均要求明确工作区上下文。
- [ ] 无参调用不会写入全局当前工作区。
- [ ] 响应和日志包含实际 `workspace_id` 及 `resolved_by`。
- [ ] MCP 会话切换工作区后必须重新绑定或确认。

## SSE

- [ ] A、B 工作区均有运行时，A 的连接收不到 B 的事件。
- [ ] 事件全部包含 `run_id`、`workspace_id`、`revision` 和唯一 `event_id`。
- [ ] 断线重连及 `Last-Event-ID` 重放不会混入其他工作区事件。
- [ ] 客户端遇到工作区或 revision 不匹配时丢弃事件并重新获取快照。

## 迁移与恢复

- [ ] 旧 `canvas.json` 和 `canvas.revision` 迁移后内容与摘要一致。
- [ ] 目标文件损坏且旧文件完整时，系统停止并报告冲突，不删除旧文件。
- [ ] 在复制、校验、rename 等每个阶段注入崩溃，重启后仍能恢复或继续迁移。
- [ ] 索引损坏不会覆盖有效备份，也不会把未完成迁移误判为完成。
- [ ] 重复启动迁移不会重复移动、删除或覆盖数据。

## 会话、深链与删除

- [ ] handoff 默认目标为来源工作区；跨工作区导入必须显式确认。
- [ ] 深链能准确打开指定工作区；不存在时明确报错，不回落成功。
- [ ] 删除非当前工作区不影响其他工作区；删除最后或唯一工作区的策略与 UI 一致。
- [ ] 删除后索引、画布文件、运行记录及孤儿产物状态一致，可审计且可恢复。

**最终结论：当前实现具备多工作区的目录隔离基础，但尚不具备并发安全、异步绑定正确、MCP 写隔离、迁移可恢复、SSE 不串台这五项完成条件。在上述阻断项通过验收前，不应将“多工作区已完整落地”视为可发布结论。**
