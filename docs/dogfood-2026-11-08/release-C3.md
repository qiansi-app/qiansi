## 核验与修改意见

**方案主张：** 上游版本已覆盖断点续跑、自动续跑、旗舰复盘、多模型讨论及可靠性改进，但部分表述需要收紧，尤其不能把自动续跑写成无条件行为。

**主要反对意见与最可能被推翻的地方：**

1. **“只重跑没有产出的任务”仍可能重复副作用。**  
   反例：某任务已经调用外部接口，但因结果文件写入前进程崩溃，被判断为“无产出”而再次执行。  
   **最可能被推翻的地方：** “无产出”必须同时参考输出记录与副作用账本，否则该结论不成立。

2. **自动续跑的作用域若记录不严谨，可能恢复人为停止的运行。**  
   反例：服务重启时只看到 `aborted`，未区分“服务中断”和“用户停止”，从而错误排队续跑。  
   **最可能被推翻的地方：** “服务重启后自动接着跑”仅适用于带 `autoResume` 意图且确由上次进程中断的运行。

3. **模型档案缺失时直接采用节点当前配置，可能改变续跑链路。**  
   反例：上一轮使用旗舰模型，节点后来切换为另一模型且未配置可用 Key，续跑无法启动。  
   **最可能被推翻的地方：** “优先沿用上一轮模型档案”依赖档案完整、可解析且对应 Key 仍可用。

4. **旗舰复盘的评分口径可能影响讨论触发条件。**  
   反例：任务均无有效验收分时，“平均验收分 < 0.6”无法计算。  
   **最可能被推翻的地方：** 触发条件中的“平均验收分”需要明确有效样本和缺分处理口径。

5. **“创建即落盘”若未保证原子写入，仍可能丢失运行记录。**  
   反例：进程在状态写入完成前被强制终止，重启后查不到该运行。  
   **最可能被推翻的地方：** 记录创建与任务启动之间必须有可恢复的持久化边界。

6. **副作用补投若缺少幂等保护，可能重复执行。**  
   反例：外部写入已成功，但本地账本在提交前崩溃；启动补投会再次写入。  
   **最可能被推翻的地方：** “启动时自动补投缺失项”只有在效果可去重或具备幂等键时安全。

**主张成立条件：**

- 续跑资格同时依据产出状态和副作用账本判断。
- `autoResume` 意图、停止原因和自动续跑轮数均被可靠持久化。
- 上一轮模型档案完整，或节点当前模型与 Key 可实际使用。
- 复盘评分对无有效分数、失败任务和部分完成任务有确定口径。
- 运行记录持久化具备原子性，副作用补投具备幂等性。
- GitHub 推送信息不放入用户说明；它不描述产品能力，且“提交 534e1ee 起”语义不够明确。

## 三、面向用户的使用说明

### 什么时候需要手动续跑？

运行失败或中断后，如果没有通过 `autoResume` 意图安排自动续跑，可以手动发起。人为停止的运行不会触发自动续跑；事实卡未明确其能否手动续跑，因此发布说明中不作承诺。

### 怎么发起续跑？

1. **界面：** 打开「需要人工」面板，在失败或中断条目上点击「续跑」。
2. **聊天/API：** 通过 `run.start` 发起续跑，并使用 `resumeOf` 指定原运行。
3. **MCP：** 调用 `resume_project` 发起续跑。

事实卡未提供 `run.start` 与 `resume_project` 的完整参数结构，发布时不要补写未经确认的字段。

### 续跑会执行什么？

- 只重新执行没有产出的任务。
- 已完成任务的产出自动作为上游上下文注入。
- 续跑任务附带「恢复说明」。
- 优先沿用上一轮的模型档案；档案缺失时，使用画布节点当前模型与 Key。

### 什么情况会自动续跑？

- 运行带 `autoResume` 意图，并在失败或中断后自动续跑，最多 2 轮。
- 服务重启后，被上次进程中断且带该意图的运行自动恢复。
- 人为停止的运行不参与自动续跑。

### 续跑后能看到什么？

每轮结束由旗舰模型复盘，运行结果中包含 `verdict`、`score`、`suggestions` 和 `action`。存在任务失败或平均验收分低于 0.6 时，系统发起一轮多模型讨论，转录写入画布产物「讨论 · 为什么没达标」。
