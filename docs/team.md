# 团队模式：一人一职、手册广播、自治档位

2026-11-12。借鉴 Grok Bot 的「bot 团队」模式：不是一个万能助手，而是一组有名字、
各管一件事的成员，加上一本所有人都必须遵守的手册。每条设计都对应他们踩过的坑
（见 [grokbot-lessons.md](grokbot-lessons.md)）。

## 名册

每张画布一个团队，存在 `~/.qiansi/workspaces/<id>/team.json`：

| 字段 | 含义 |
|---|---|
| `name` | 称呼。讨论、分派、报告里都用它 |
| `job` | **唯一职责**，一句话。不是「通用助手」 |
| `autonomy` | 自治档位：调查 / 草稿 / 执行 / 全权 |
| `tools` | 能力（工具白名单）：读文件、写文件、终端、画布查询、联网 |
| `model` | 默认模型（可空） |
| `memory` | 这个成员的长期记忆：偏好、约定、踩过的坑 |

规则（保存时强制）：

- 称呼不能重复；职责不能完全相同；职责描述互相包含只提醒不阻止；
- 成员上限 12 人；超过 8 人给出提醒——先问「现有成员能不能兼任」再新建；
- 空手册、手册过长、没有成员都会提醒。

## 手册广播

`playbook` 是团队标准，写一次、所有成员都读。运行时它被注入每个 worker 的系统提示
（与画布公共指令并列），也进入编排器的提示词和评委的「团队身份」段落。
成员个人记忆只注入该成员自己的任务，不广播。

这是他们「标准只写一次、由一个人拥有、广播给所有人」的落地。
手册里写标准（交付必须附证据、不确定的数字标来源），不写某一次事故的故事。

## 主控就是幕僚长

自动编排（`/api/workflow`）会收到名册与手册：

- 每个工作节点带 `member`（成员称呼），必须是名册里的人；
- 规划规则第 15 条：按唯一职责匹配，不按人名凑；同一个成员可以接多个相关节点，
  但不要把与他职责无关的任务塞给他；名册里没有合适人选就留空；
- 审校者多查一件事：成员分配是否把任务塞给了职责不符的人；
- 节点落到画布后带 `memberId` / `memberName`，运行时的任务提示词里就带上了
  该成员的身份、档位和记忆。

实测：目标是「先核对三条事实，再写一段说明」，名册为「小核（核实事实与来源）」
与「小稿（写初稿并给出结构）」，主控分成三个节点并分别指派给小核、小稿、小核。

## 自治档位是真的约束

| 档位 | 能做什么 | 工具 |
|---|---|---|
| 调查 | 只读与检索，产出结论 | `read_file` / `list_dir` / `describe_canvas` / `get_canvas` / `list_*` / `get_run_result` / `web_search` |
| 草稿 | 只读，产出修改提案 | 同上 |
| 执行 | 读写工作目录、跑命令 | 全部工具（危险命令仍拒绝） |
| 全权 | 执行 + 画布操作 | 全部工具 |

约束做在两层：给模型的工具清单里根本没有写文件/跑命令；即使模型硬要调用，
执行器也会返回「档位不允许」。不靠提示词自觉。

## 能力（工具白名单）

除了档位，每个成员还有一组**能力**：读文件、写文件、终端、画布、联网。
界面上是五个开关；服务端把它翻译成工具白名单，并在运行时同时按「档位」和
「成员能力」收紧工具箱——没开通 `write_file` 的成员，连工具都看不到，
硬调也会被拒绝并提示「请在团队会议里申请」。

- 调查/草稿档位只能开通只读能力（读文件、画布、联网），写文件/终端会被禁用；
- 空能力列表是合法的：这个成员只能纯文本交付；
- 能力会写进任务提示词（「可用工具：…」），成员知道自己的边界；
- 编排计划里的 `toolAllow` 来自成员能力，运行时按任务生效。

## 团队会议

弹窗里的「开会」现在是**逐成员流式**的：

- 服务端按顺序让每个成员发言，逐个推送「开始 / 发言完成 / 失败」事件；
- 界面为每个成员保留一张卡，显示头像、职责、模型和状态（等待 / 发言中 / 已发言 / 失败）；
  发言一完成就显示内容，不需要等整场会议结束；
- 标题旁显示「2/3 已发言」进度；某个成员模型不可用（欠费、超时）只会让这一张卡失败，
  会议继续，其他成员的反馈照常显示；
- 成员**缺少工具**时，可以在发言末尾申请：
  `TOOL_REQUEST: list_dir、run_command | 定位文件并验证行为`（一行可申请多个工具）。
  服务端解析成结构化提案，界面显示「谁申请了什么、为什么」，用户点「批准并添加」才写入能力；
- 会议使用服务端已保存的名册；有未保存修改时按钮会禁用并提示先保存。

实测里，两个成员对同一议题给出了不同判断（第二个开头就是「我有个分歧」）；
一个只读权限的成员主动申请了「看目录」和「运行命令」，批准后能力立刻变为 3 项。
另一次会议里 GLM 账户余额不足，只有该成员显示失败原因，其他成员正常完成。

## 界面交互（本轮优化）

- 成员卡改为「头像 + 称呼 + 职责 + 模型/档位 + 能力开关」的紧凑结构；
- 模型下拉以**服务端密钥目录**为准（不会再出现「deepseek-flash 未在目录中」），
  已停用的厂商标注「已停用」；
- 能力分组支持部分开通（虚线勾选），点击补齐/关闭；
- 本地校验：空称呼、重名、职责完全相同会即时列出并禁用保存；
- 未保存修改显示「未保存」标记；关闭时先确认，避免误丢改动；
- 新的工具申请出现时自动滚到申请区，避免藏在长列表底部。

## 界面

- 工具栏「更多」→ **团队名册与手册**（徽标显示成员数）：编辑手册、名册、档位、记忆，
  现场开会；
- 点一个模型节点 → 抽屉「能力」→ **团队成员**：把节点指派给某个成员（或不指派）；
- 自动编排弹窗会显示「任务会优先交给团队名册里的 N 名成员」；
- 委托任务与接续会话新建画布时，名册与手册一起带过去。

## 接口

- `GET /api/team?ws=` → `{ ok, team: { playbook, members, warnings, cap } }`；
  `members[].tools` 是能力白名单（缺省表示沿用档位）；
- `PUT /api/team`（body 为 `{ members, playbook }`）→ 校验失败 400，带 `error` / `hint`；
  未知工具会被丢弃，成功返回规范化后的团队与提醒；
- `POST /api/team/meeting`（`{ topic, memberIds? }`）→ **SSE 流**：`meeting.started`、
  `member.started`、`member.finished`、`member.failed`、`meeting.finished`；
  `meeting.finished.proposals` 是解析出的工具申请（`memberId/memberName/tool/toolLabel/reason`）；
- `/api/workflow` 新增可选 `team`（`[{ id, name, job, model }]`）与 `playbook`；
- `/api/discuss` 的 `participants[]` 新增可选 `role`（通用讨论，不解析工具申请）。

## 已知限制

- 成员记忆是手写的，不会自动从运行里学习；「团队记忆」目前是提示词，不是独立上下文。
- 「全权」与「执行」目前工具集合相同，画布级操作还没有单独开放。
- 会议不会自动生成主控结论；发言原文与申请列表给用户，是否采纳由人决定。
- 团队按画布隔离；跨画布共享一套团队还没有做（委托/接续会复制一份）。
- 名册不阻止给同一个成员派多件事——只做职责匹配与提醒，判断留给人。
- 会议只支持一轮；工具申请由模型主动提出，不保证每场会议都会出现。
